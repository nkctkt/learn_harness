# /incident — バグは「ハーネスの穴の発見」として扱う

修正そのものより、**「なぜ hook / pre-commit / CI が止めなかったか」** を記録して次に活かすのが目的。
`docs/exercises/` の「意図的欠陥 → 検出 → 修正」と同じ形を、意図しない欠陥に適用する。

## 手順

1. **記録を作る**(ゲートは通常どおり。ただし短い)
   ```
   scripts/intent.sh new <slug> --scope bugfix
   ```
   `intent.md` の目的に **症状・再現手順・影響範囲(誰に / どのデータに)** を書く。受け入れ条件は「`<test名>` が通る」+「既存の suite が緑のまま」。HITL は影響範囲で決める(データ破壊・秘密情報なら 5 = 人間に引き継ぐ)。
   `gate present intent` → ターンを終える。
2. **plan.md は 2 unit 固定**
   ```yaml
   units:
     - name: u1-reproduce      # 落ちるテスト(単体で再現できなければ結合 / 契約テスト)
       depends_on: []
     - name: u2-fix            # 最小修正。u1 が通る
       depends_on: [u1-reproduce]
   ```
   DoD: u1 = 「修正前に落ち、修正後に通るテストがある」、u2 = 「u1 と既存 suite が緑、`verify.sh` 全体が通る」。
   `gate present plan` → ターンを終える。
3. **u1: 再現テストを先に**(`/build-unit u1-reproduce`)。再現できないバグは直せたか分からない。ログしか無い時は、ログの状況をテストの入力にする。
4. **u2: 最小修正**(`/build-unit u2-fix`)。ついでのリファクタはしない(スコープ外に書く)。
5. **ポストモーテムを `retro.md` に書く**(`/retro` の一部として)
   | 項目 | 内容 |
   |---|---|
   | 時系列 | 発見 → 再現 → 修正 |
   | 根本原因 | コードの原因(1 文)と、**プロセスの原因**(なぜ書かれたか) |
   | 捕まえるべきだった層 | 型 / lint / 単体 / 結合 / 契約 / SAST / レビュー のどれか。その層に何が足りなかったか |
   | ハーネスの変更 | テスト追加(必須)+ 可能なら決定論的な検査(Semgrep ルール、Rego、hook、verify の段) |
   | 検出できるようになった欠陥 | 同種の欠陥を意図的に作り、新しい検査が落とすことを確認した結果 |
6. `/create-pr` → merge → `/retro` → `close`。

## 判断の基準

- 「テストを足す」で終わらせない。同じ種類の欠陥を **書けなくする** 検査(決定論的)があるか毎回考える。無ければその理由を書く。
- 秘密情報の漏洩・データ破壊が絡む場合は Agent が続けない。状況を書いてターンを終え、人間に引き継ぐ(HITL-5)。
